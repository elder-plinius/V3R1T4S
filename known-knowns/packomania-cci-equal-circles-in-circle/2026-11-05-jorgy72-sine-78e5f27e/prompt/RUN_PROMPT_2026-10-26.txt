- Effort: standard, about 3 hours. Long computations run at low priority (nice),

  goes under "Needs you" in REPORT.md.

  No submission is ever made to a record table; a claim is for the verified
  construction only.

- One target, two to four lenses, real code, every run. No exceptions.
- Write the evaluator before the search. Search speed is the edge.

- A clean "no" is a good night. Never stretch a near-miss into a claim.

## The circle-packing criterion (bank text, for q-pack-cci)

Success means a file of N centers (x_i, y_i) for one N listed in the live
radius table such that the FEASIBLE radius r* := min(min_{i<j} |c_i - c_j| / 2,
1 - max_i |c_i|), computed in mpmath at 50 digits directly from the submitted
coordinates (no tolerance), is STRICTLY GREATER than the live table radius for
that N re-fetched immediately before claiming, by at least 1e-11, AND the
configuration is not isometric to the posted seed (sorted pairwise-distance
multisets differ), AND N does not appear in a History-of-updates line newer
than the one the scout fetched. QUEUE RULE: N must NOT lie inside any range
listed for this category on the live pending-requests page re-fetched at
verification time; a value already in the queue does not count as ours.
Standing caveat, always stated: the 26-Sep-2026 Moki & Julio "*many*"
4666-candidate bundle is category-unspecified; the N must be re-checked
against the live table once that bundle disappears from the pending list.
Coordinates are CENTERED (container centre at the origin, container radius 1).
Bank partial wins: p1 = second optimum within 1e-11 for N in 1..2600,
certified non-isometric; p2 = certified improvement for a gap value N > 2600
with a lattice-like seed; p3 = certified improvement in the sibling
regular-hexagon table chx (N <= 1261, 12 decimals, margin 1e-10).

Pitfalls: the margin rule is absolute — a double-precision improvement below
1e-11 is a NEGATIVE. The 50-digit checker is O(N^2), so use fast
double-precision evaluators inside the search loop and certify only
finalists. Re-verify the pending-requests page immediately before any claim.

## Lenses

Run the skeptic lens first, then attack lenses. A lens with nothing after
three runs gets rotated out.

- already-settled (skeptic): your job is to kill the quarry — check the table,
  the recent literature, the repo's trophy case. A quarry that survives you

- Attack lenses, picked from the run brief's concrete angles and the charter

## Judge and panel

- A lens result is negative unless it clears the preregistered bar at full
  precision. Float margins below the bar are negatives, not wins.
- If a candidate clears the bar, convene a three-skeptic panel (one
  non-author argues against, the author answers, 24h with no open objection
  in the panel record is not available overnight — so record the panel as
  convened with objections open, and mark the claim at most PROMISING unless
  the panel record closes clean).
- Write runs/<YYYY-MM-DD-HHMM>/panel/gate.md as the honesty gate: status
  (NOTHING / PROMISING / CONFIRMED_*), confirmed scope, and what was panelled.
- Kill criteria: target confirmed solved or closed at a primary source (dead,
  logged, never revisited without new evidence); a decoy beats the claim in
  the null test (dead on the spot); no fresh contexts available for the panel
  (claim stays PROMISING, never packaged); check_run.py does not print
  CHECK_RUN: PASS (nothing reported, fix the run); compute exceeds the night's
  budget twice running (shrink the target or drop it); a skeptic falsifies a
  lens's core assumption (retire that lens for that quarry).
