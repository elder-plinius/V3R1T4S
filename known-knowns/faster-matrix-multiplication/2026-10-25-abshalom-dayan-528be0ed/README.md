# fmm-catalogue-small-format-rank: partial win p1, <30,30,31> rank 12395 over Q

## What
The joined object files (sha256 u 528be0ed8aa1..., v da65b90d20b3..., w c53a02a35df8...) define a bilinear scheme over Q with exactly 12395 rank-one terms for <30,30,31> whose 778410000 Brent equations I verified exactly, and 12395 is strictly below both the live fmm_sota.json entry (12789) and the live Lille per-format page (13610) fetched 2026-10-25, is not a listed Lille construction, and is below every value for this format I found in those tables, the Lille index, matmulcatalog and the V3R1T4S pull requests, so it meets partial win p1 (not the main criterion).

Path note: the panel files, how-we-built-it/PREREG.md and verify-it-yourself/RECEIPTS.md refer to the run's claim folder, claim/. There, CLAIM.md is README.md as gated (same What sentence), REPRODUCE.md is RUN_IT_YOURSELF.md, and object/, verify-it-yourself/ and the-record-we-beat/ are the folders of the same names here. Work files and folders named in those files, in how-we-built-it/COMMANDS.md and in the-record-we-beat/FETCH_LOG.txt (STATEMENT.txt, panel/claim.sha256, cells/, data/, fetch_log.txt, attempts/, and the save folders tables/, prs/ and lit/) are not shipped; the comparator records are in the-record-we-beat/. The band run named in COMMANDS.md and PREREG.md is the run that built the cells of this batch.

Claimed as partial win p1; the three skeptic reports are in panel/. The scheme is A 30x30 times B 30x31. It comes from Khoruzhii, Serafin, Gelss and Pokutta's published LITA 31^3 rank-13433 scheme by two exact non-coordinate one-slice restrictions, each followed by one exact 2-reduction; the first restriction passes through the sibling <30,31,31> scheme (a separate package of this batch). The rebuild from LITA's file was done only once, so determinism of the rebuild was not checked for this cell (see Not claimed); the object itself is fixed by its sha256 and verified exactly.

Margin: 394 below the lowest public value for this format (12789), 394 below the two tables (12789). One fresh panel subagent per role (REPRODUCE, NOVELTY, CRITERION) judged all 12 cells of this batch (panel/gate.md).

## Check it yourself
From this folder, in a fresh shell (python3, standard library, no network; numpy only for the optional second checker):

    sh verify-it-yourself/run_checks.sh

Expected last line: `PASS`. About 230 s wall for the whole script (check 1 about 219 s, check 2 about 10 s) on a laptop, peak memory about 3.8 GB resident for this cell (up to about 3.8 GB on the largest cell of this batch); it is check 1, the stdlib checker, that needs this; check 2 needs about 0.7 GB (measured numbers: verify-it-yourself/RECEIPTS.md). Another run on a shared machine took peak memory 3.51 GB. The script joins the parts in object/ into u.txt, v.txt and w.txt, checks their sha256, then runs two exact checkers: check_brent_stdlib.py (python3 standard library only) checks all 778410000 Brent equations (30*30 * 30*31 * 30*31 index triples) in integer arithmetic after multiplying each factor matrix by its least common denominator, and evaluates the scheme on three random integer matrix pairs exactly; check_exact_np.py (numpy) is a separately written exact checker of the same equations, much faster, with its own exactness argument in its docstring (it is skipped with a message if numpy is not installed, and then the verdict rests on the first checker alone). In this batch check_exact_np.py has an exact Python-integer path for terms too large for float64 (the version in the earlier 8-cell packages stops with an assertion on such terms; this one was tested against the <18,18,19> negative controls, see RECEIPTS.md). On this cell check 1 (check_brent_stdlib.py, standard library only, pure integer arithmetic) is the main check and the memory-heavy one: budget the peak memory stated above on the machine that runs it. The stdlib checker is the one from the <18,18,19> package (PR #714); that package's second stdlib checker (check_scheme_second.py) is not shipped here, to keep the batch to the two checkers above. This package's check_exact_np.py has sha256 prefix 0eeb12c7; the eight earlier packages of the batch (<20,20,21> to <26,27,27>) ship the version with prefix 3f9ebe84. RUN_IT_YOURSELF.md has the file format and the full expected output; how-we-built-it/COMMANDS.md rebuilds the object from LITA's published scheme.

### How 12395 relates to the listed values
- 12789 (tables) is the block sum ⟨30×30×1:900⟩ + ⟨30×30×30:11889⟩ (naive 30x30x1 plus LITA's 30^3 scheme) as the Lille construction column writes it.
- From LITA's <31,31,31> rank 13433, plain coordinate projections (delete one index, drop the terms that vanish, no reductions) give at best 13309 for <30,30,31> (delete row 15 and column 15: 124 terms vanish); from the sibling 12906 scheme (<30,31,31>), the best single-coordinate deletion of that sibling scheme (every deletion of one index in either of its two size-31 axes, dropping the terms that vanish, no reductions; counted in panel/criterion.md) gives 12845 terms. All are above the table value 12789.
- This scheme uses non-coordinate slices instead. Slice 1 (row index shared by A and C; direction e* = (1,...,1,-13,1,...,1), -13 at index 15, on the A side and e_0 on the C side) kills 526 terms (480 on the A side, 46 on the C side, none on both): 13433 - 526 = 12907; one exact 2-reduction gives 12906 (<30,31,31>, the sibling cell). Slice 2 (column index of A = row index of B; e_0 on the A side, e* on the B side) kills 510 terms (31 + 479, none on both): 12906 - 510 = 12396; one exact 2-reduction gives 12395. Total removed: 526 + 1 + 510 + 1 = 1038 = 13433 - 12395.

Correction to the figure in how-we-built-it/slice_accounting_output.txt: that file's "best column" line (12859 terms) counts only deleting a column of A together with the matching row of B. The panel's count in panel/criterion.md covers every single-coordinate deletion of the sibling scheme and gives 12845 terms; both are above this cell's rank 12395.

## Prior work on this method
The LITA slice-and-absorb method is not new in this repository. Earlier p1 claims with this slice method (PRs #41 to #51) were closed unmerged by their author on 2026-10-14 (12:51Z), together with about 115 of that author's other early pull requests, including main-criterion claims refiled and merged the next day (#130, #164); no maintainer comment or verdict on them exists. No p1 claim of this method has been merged yet, but the repository's own TROPHY_CASE rows 44 to 48 are restrictions of LITA squares. The merged PRs #130, #164, #172 and #197 (2026-10-15 and 2026-10-16, from LITA 15^3 and 17^3), and the merged LITA-based claims #166, #175, #177, #178 and #179, were for formats with max dimension at most 16. PRs #708 (<18,19,19> rank 3424) and #714 (<18,18,19> rank 3225) are open sibling claims by the same contributor with the same method, from LITA 19^3. What is new here is this format's value 12395 and this scheme. The rebuild of this scheme from LITA's file was run only once (no determinism check), unlike the 19^3 claims; see Not claimed.

## Not claimed
- Not the main criterion: max(30,30,31) = 31 > 16. Partial win p1 only.
- Not the tensor rank of <30,30,31>: 12395 is an upper bound (a scheme with 12395 multiplications), not a proof that fewer are impossible.
- Not a ring upgrade: the coefficients are rationals (denominators up to 28224); nothing is claimed over Z or GF(2).
- Not a new method. The same LITA non-coordinate slice with exact absorption was used earlier in this repository: PRs #41 to #51 (earlier p1 claims with this slice method, closed unmerged by their author on 2026-10-14, with no maintainer comment or verdict) and the merged PRs #130, #164, #172 and #197 (2026-10-15 and 2026-10-16; from LITA 15^3 and 17^3), and, for the 19-family from LITA 19^3, PR #708 (<18,19,19> rank 3424) and PR #714 (<18,18,19> rank 3225), both open. Only the value 12395 for this format, with this scheme, is new here.
- Not the sibling cells of this batch (one cell per claim): <30,31,31> rank 12906.
- Reproducibility of the rebuild: not checked for determinism. The rebuild of this N was done once (N = 31: one rebuild took 5165 s and 5.55 GB RSS; no second rebuild was run). Determinism of the rebuild is therefore not confirmed for this cell. The object itself is fixed by its sha256 and checked exactly, so the claim does not depend on it, but a skeptic cannot treat the rebuild as proven reproducible.
- The Lille page for this format (13610) is older than the index; the claim does not rest on it alone, since 12395 is below every value in every source read.
