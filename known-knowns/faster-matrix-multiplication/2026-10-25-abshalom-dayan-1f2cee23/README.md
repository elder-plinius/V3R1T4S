# fmm-catalogue-small-format-rank: partial win p1, <26,27,27> rank 8828 over Q

## What
The joined object files (sha256 u 1f2cee23872a..., v 9b2bbcffa370..., w e1df758b5c8b...) define a bilinear scheme over Q with exactly 8828 rank-one terms for <26,27,27> whose 359254116 Brent equations I verified exactly, and 8828 is strictly below both the live fmm_sota.json entry (9233) and the live Lille per-format page (10036) fetched 2026-10-25, is not a listed Lille construction, and is below every value for this format I found in those tables, the Lille index, matmulcatalog and the V3R1T4S pull requests, so it meets partial win p1 (not the main criterion).

Path note: the panel files, how-we-built-it/PREREG.md and verify-it-yourself/RECEIPTS.md refer to the run's claim folder, claim/. There, CLAIM.md is README.md as gated (same What sentence), REPRODUCE.md is RUN_IT_YOURSELF.md, and object/, verify-it-yourself/ and the-record-we-beat/ are the folders of the same names here. Work files and folders named in those files, in how-we-built-it/COMMANDS.md and in the-record-we-beat/FETCH_LOG.txt (STATEMENT.txt, panel/claim.sha256, cells/, data/, fetch_log.txt, and the save folders tables/, prs/ and lit/) are not shipped; the comparator records are in the-record-we-beat/. The band run named in COMMANDS.md and PREREG.md is the run that built the cells of this batch.

Claimed as partial win p1; the three skeptic reports are in panel/. The scheme is A 26x27 times B 27x27. It comes from Khoruzhii, Serafin, Gelss and Pokutta's published LITA 27^3 rank-9233 scheme by one exact non-coordinate one-slice restriction, followed by one exact 2-reduction. The rebuild from LITA's file was done only once, so determinism of the rebuild was not checked for this cell (see Not claimed); the object itself is fixed by its sha256 and verified exactly.

Margin: 351 below the lowest public value for this format (9179), 405 below the two tables (9233). One fresh panel subagent per role (REPRODUCE, NOVELTY, CRITERION) judged all 12 cells of this batch (panel/gate.md).

## Check it yourself
From this folder, in a fresh shell (python3, standard library, no network; numpy only for the optional second checker):

    sh verify-it-yourself/run_checks.sh

Expected last line: `PASS`. About 77 s wall for the whole script (check 1 about 73 s, check 2 about 4 s) on a laptop, peak memory about 1.3 GB resident (the stdlib checker; the numpy one needs less) (measured numbers: verify-it-yourself/RECEIPTS.md). The script joins the parts in object/ into u.txt, v.txt and w.txt, checks their sha256, then runs two exact checkers: check_brent_stdlib.py (python3 standard library only) checks all 359254116 Brent equations (26*27 * 27*27 * 26*27 index triples) in integer arithmetic after multiplying each factor matrix by its least common denominator, and evaluates the scheme on three random integer matrix pairs exactly; check_exact_np.py (numpy) is a separately written exact checker of the same equations, much faster, with its own exactness argument in its docstring (it is skipped with a message if numpy is not installed, and then the verdict rests on the first checker alone). The stdlib checker is the one from the <18,18,19> package (PR #714); that package's second stdlib checker (check_scheme_second.py) is not shipped here, to keep the batch to the two checkers above. This package's check_exact_np.py has sha256 prefix 3f9ebe84; the four later packages of the batch (<28,28,29> to <30,31,31>) ship a version with prefix 0eeb12c7 that adds an exact Python-integer path for terms too large for float64. RUN_IT_YOURSELF.md has the file format and the full expected output; how-we-built-it/COMMANDS.md rebuilds the object from LITA's published scheme.

### How 8828 relates to the listed values
- 9233 (tables) is the Lille and fmm_sota.json value: LITA's <27,27,27> rank 9233 projected (the Lille construction column writes Proj([[27, 0], [0]], ⟨27×27×27:9233⟩)); matmulcatalog derives 9179 from the same scheme by deleting the best row (index 13: 54 terms vanish; reproduced in how-we-built-it/slice_accounting_output.txt).
- From LITA's <27,27,27> rank 9233, plain coordinate projections (delete one index, drop the terms that vanish, no reductions) give at best 9179 for <26,27,27> (delete index 13: 54 terms vanish). This scheme uses a non-coordinate slice instead: the slice (row index shared by A and C; direction e* = (1,...,1,-11,1,...,1), -11 at index 13, on the A side and e_0 on the C side) kills 404 terms (364 on the A side, 40 on the C side, none on both): 9233 - 404 = 8829; one exact 2-reduction gives 8828. Total removed: 405.

## Prior work on this method
The LITA slice-and-absorb method is not new in this repository. Earlier p1 claims with this slice method (PRs #41 to #51) were closed unmerged by their author on 2026-10-14 (12:51Z), together with about 115 of that author's other early pull requests, including main-criterion claims refiled and merged the next day (#130, #164); no maintainer comment or verdict on them exists. No p1 claim of this method has been merged yet, but the repository's own TROPHY_CASE rows 44 to 48 are restrictions of LITA squares. The merged PRs #130, #164, #172 and #197 (2026-10-15 and 2026-10-16, from LITA 15^3 and 17^3), and the merged LITA-based claims #166, #175, #177, #178 and #179, were for formats with max dimension at most 16. PRs #708 (<18,19,19> rank 3424) and #714 (<18,18,19> rank 3225) are open sibling claims by the same contributor with the same method, from LITA 19^3. What is new here is this format's value 8828 and this scheme. The rebuild of this scheme from LITA's file was run only once (no determinism check), unlike the 19^3 claims; see Not claimed.

## Not claimed
- Not the main criterion: max(26,27,27) = 27 > 16. Partial win p1 only.
- Not the tensor rank of <26,27,27>: 8828 is an upper bound (a scheme with 8828 multiplications), not a proof that fewer are impossible.
- Not a ring upgrade: the coefficients are rationals (denominators up to 16400); nothing is claimed over Z or GF(2).
- Not a new method. The same LITA non-coordinate slice with exact absorption was used earlier in this repository: PRs #41 to #51 (earlier p1 claims with this slice method, closed unmerged by their author on 2026-10-14, with no maintainer comment or verdict) and the merged PRs #130, #164, #172 and #197 (2026-10-15 and 2026-10-16; from LITA 15^3 and 17^3), and, for the 19-family from LITA 19^3, PR #708 (<18,19,19> rank 3424) and PR #714 (<18,18,19> rank 3225), both open. Only the value 8828 for this format, with this scheme, is new here.
- Not the sibling cells of this batch (one cell per claim): <26,26,27> rank 8437.
- Reproducibility of the rebuild: not checked for determinism. The rebuild of this N was done once (N = 27: one rebuild took 1653 s and 2.44 GB RSS; a second was started and aborted after about 20 s). Determinism of the rebuild is therefore not confirmed for this cell. The object itself is fixed by its sha256 and checked exactly, so the claim does not depend on it, but a skeptic cannot treat the rebuild as proven reproducible.
- The Lille page for this format (10036) is older than the index; the claim does not rest on it alone, since 8828 is below every value in every source read.
